# TOPページ再構成 計画案

> 本ドキュメントは TOP ページ（`app/(marketing)/page.tsx`）の再構成計画。
> UI 実装は本計画を仕様として別途進行する想定。コピー（文言）は本計画の方向性に沿いつつ、最終文言はレビューを通すこと。

## 0. コンセプト（背骨）

3 本柱を主役に据えたうえで、**時間軸＝法改正の締切**を重ねる。

> 「使われる福利厚生」ではなく **「2028 年の義務化に、社宝 1 本で備える」** を背骨にする。

人事が予算を動かすトリガーは「便利さ」ではなく「やらないと罰則・締切がある」こと。3 本柱のなかでも **ストレスチェック（法定義務）を入口アンカー**にし、健康経営認定・福利厚生を「どうせやるなら同じアプリで」と束ねる。これが社宝唯一の構造的強み。

### 前提となる市場ファクト
- 2025 年 5 月公布の改正労働安全衛生法により、**ストレスチェック義務が 50 人未満の全事業場に拡大**。施行日 **2028 年 4 月 1 日**、第 1 回実施期限 **2029 年 3 月 31 日**。
- → これが数年に一度級の追い風。LP の背骨に据える。

## 1. 守るべき制約（CLAUDE.md 準拠・必須チェック）

実装・コピー作成時、以下 3 点を全文言でチェックすること:

1. **医療断定の禁止** — 「治る」「改善する」等の効果断定をしない。
2. **法的断定の禁止** — 「確実に完了」「これで義務対応は万全」等を避け、「法令に沿って実施・報告まで支援」と表現。
3. **競合誹謗・実名比較の禁止** — Benefit One / Relo / SmartHR 等の実名比較表は作らない。カテゴリ比較（「福利厚生代行サービス」「ヘルスケアアプリ単体」）で独自性を示す。
4. **根拠のない統計の禁止** — 出典のない「導入率◯%」等を載せない。

ターゲットを「50 名以上」に限定するコピーは入れない（2028 年以降の 50 人未満市場を自ら締め出すため）。

## 3. 各セクションの仕様（コピー方向＋必要素材）

### 1. Hero
- **最上部に締切バッジ**:「2028 年、ストレスチェックが全事業場で義務化へ」
- **メインコピー案**:「ストレスチェックも、健康経営も、福利厚生も。― 3 つの義務と課題を、社宝ひとつで。」
- **サブ**:「法定対応から健康経営認定支援まで、ひとつのアプリで整えます。」（「50 名以上」は入れない）

- 既存ヒーロー画像（アプリ利用シーン）は右側に維持。
- 素材: コピーのみ。

### 2. 信頼バー（現 SocialProof / 位置維持）
- 健康経営優良法人 2026（認定番号 139686）、SECURITY ACTION 二つ星、AWS、IT 導入補助金（申請状況に応じ表記）。
- Hero 直下＝最も疑念が生まれる瞬間に信頼担保を置く。**後半へ移動しない。**

### 3. 課題提示（現 Stats 刷新）
3 本柱に 1 対 1 対応する痛みに差し替え（並び順も柱と対応させる）:
- 「毎年のストレスチェック、集計と労基署報告に追われている」→ 柱①
- 「健康経営優良法人を取りたいが、証跡集めで挫折する」→ 柱②
- 「福利厚生を入れても、使う人と使わない人の差が大きい」→ 柱③

### 4. ★ 3本柱（現 FeaturesOverview 全面作り直し / 主役）
縦並び大型カード 3 枚。各カード = 強調ポイント＋実装済み機能＋solution ページへのリンク。**柱ごとに色を固定**（①青 / ②緑 / ③橙）し、以降のセクションでも同色で参照させる。視覚的ヒエラルキーでここが見せ場と明示する。

- **柱① ストレスチェック（法定義務）** — 実施〜集計〜産業医面接フロー〜労基署提出用 XML 出力まで一気通貫。10 名未満非開示の集団分析も自動。法改正対応済み。
  - コピー注意: 法的断定を避け「法令に沿って実施・報告まで支援」と表現。
- **柱② セルフヘルスケア × 認定支援** — 歩数・睡眠（Apple Health / Google Fit 連携、端末内保存のプライバシー設計）→ 活動記録 → 健康経営優良法人（大規模・中小規模）認定申請の証跡として活用。
- **柱③ ポイント制福利厚生** — 健康行動でポイント → 電子マネー / ギフト交換。役職・拠点・雇用形態によらず人事が条件・上限を設計 ＝「不公平感をなくす」。

### 5. 統合の優位性（現 KenkoKeiei 拡張）

- 右: 社宝 1 本 → 一元管理・運用負担減
- 「統合されていること自体が価値（＝社宝の堀）」を言語化する核セクション。

### 6. カテゴリ比較（現 Comparison 強化 / 実名なし）

この 2 軸は「福利厚生代行」「ヘルスケアアプリ単体」が × になり独自性が視覚化される。**実名は入れない。**

## 4. このUI構成に至った理由（設計意図）

1. **締切バッジを最上部に置く** — 福利厚生アプリ特有の「あれば嬉しい(=なくてもいい)」評価を、「対応必須」評価へ切り替えるため。本計画で最重視した点。
2. **信頼バーを Hero 直下から動かさない** — 関心を持った直後＝最も疑念が生まれる瞬間に信頼担保を置くのが定石。後半に下げると効きが落ちる。
3. **課題(3枚)→3本柱(3枚)を 1 対 1 対応** — 問題と解決を同じ並び順で対応させ、読者が自分の痛みの解決を一直線に追えるようにする。柱ごとの固定色で「どの柱の話か」を以降も辿らせる。
4. **3本柱カードだけ強調** — 社宝唯一の構造的強み＝ページの主役。視覚的ヒエラルキーで見せ場を明示し、強みを埋もれさせない。
5. **比較は実名なし・◯×2軸追加** — 競合誹謗・法的断定リスク（CLAUDE.md 禁止事項）を回避しつつ、「カテゴリそのものが違う」と見せる方が安全かつ強い。
6. **統合優位性に「バラバラ vs 1本」対比** — 3 本柱を並べただけでは「各機能は他社にもある」で終わる。対比があって初めて「統合されていること自体が価値（堀）」が腑に落ちる。

## 5. 実装の進め方（憲章準拠）

1. **コピー Doc を先に確定** — コードより先に文言レビュー。医療断定 / 法的断定 / 競合実名 / 根拠なき統計の 4 チェックを通す。
2. **セクション単位で PR 分割** — 例: `[AI-マーケティング部] Hero刷新`、`[AI-マーケティング部] 3本柱セクション新設`。main 直 push 禁止。
3. **大きい方針変更は単独確定しない** — 実名比較の採否等は Org Discussions で承認を取る。
